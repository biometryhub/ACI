# Contributing to aciR

Contributions are welcome. This document says what the package expects, so
that a contribution is not turned away for a reason it could not have known.

## Reporting a problem

Open an issue at <https://github.com/max578/aciR/issues>. A numerical report is
most useful with the model specification, `dt`, `mu0`, `R0`, the output of
`summary()` on the result, and `sessionInfo()`. If the metric looks wrong, say
what you expected and why. For this package that is usually the most
informative part of the report.

## The one rule that is not negotiable

**The oracle tests are a release gate.** They run the package's own filter,
smoother and metric against fixtures generated by an independent MATLAB harness
and must reproduce them to `1e-6`. They never skip. A change that breaks them
is wrong until proven otherwise, and "the test is too strict" is not a
proof. The observed agreement is at `4.6e-14`, so a change that pushes it to
`1e-6` has altered the numerics by eight orders of magnitude.

Fixtures are never regenerated to make a test pass. See the refresh policy in
`inst/extdata/oracle-manifest.yml`.

## Adding a validated capability

New numerical capability needs an oracle before it needs an implementation.
That oracle must be something the contributor did not also author: the authors'
reference implementation, an analytic solution, an established package, or a
published table. A test whose expected values came from running the new code is
a record of what the code did, not a check that it is right.

If no independent oracle is available, say so in the pull request. An explicit
`[unverified]` is a contribution; a green test that grades nothing is a
liability.

State what your oracle covers **and what it does not**. The package learned
this the hard way: the dyad fixture pins the noise cross-covariance at zero, so
it executes the terms carrying it without ever grading them, and a
99.6%-coverage figure said nothing about that gap.

## Style

R code follows the package's committed `.lintr`. Two points that trip people up:

* The numerical core uses the notation of the method paper (`L_x`, `S_xoS_x`,
  `A_j` and relatives) rather than R naming convention. This is deliberate,
  the correspondence to the published equations is what makes the code
  auditable, and the `.lintr` admits those names by a narrow rule. Do not
  rename them, and do not widen the rule to cover new ones without saying why.
* Validation goes in a named `.aci_check_*` helper in `R/aci-validate.R`, not
  inline in the function body. Errors use `stop(..., call. = FALSE)` and name
  the offending argument and index.

Run `devtools::test()` and `lintr::lint_package()` before opening a pull
request. Error messages are locked by snapshot tests; if you change one
deliberately, update the snapshot in the same commit.

## Documentation

Documentation is roxygen-generated. Run `devtools::document()` and commit the
generated `man/` files. If a change affects what the package claims about its
own evidence, it affects `inst/extdata/oracle-manifest.yml` and the
*Validation and the independent oracle* vignette too.
